# 提交规范

本文是本仓库提交规范的统一入口，[AGENTS.md](../AGENTS.md) 只保留摘要和链接。规范参考 ArchiveLens 的 `docs/commit-conventions.md`、`commitlint.config.cjs` 及安全 hook 初始化约束（2026-10-20 本地核对），并按本仓库的 npm、`dev` 主干和生成文件约定调整。

## 提交信息

普通提交使用带作用域的 Conventional Commits：

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `type`、`scope`、半角冒号、冒号后的一个空格及 `subject` 必填；正文和 footer 按需要填写。
- 标题总长度不超过 72 个字符，不含首尾空白。说明必须包含中文，技术名词可以保留英文；结尾不用中英文句号或分号。
- `scope` 表示稳定的模块，仅使用小写英文、数字及单个连字符连接的分段，不用下划线、空格或多个范围拼接。
- 正文与标题、footer 与前文各空一行。复杂改动、公共契约、权限、共享状态、兼容逻辑及多步骤交付必须写正文，说明原因、关键行为、影响和迁移条件。
- 验证命令、测试计数、构建结果和验收状态单独写入评审或验证记录，不写入提交信息。
- 不编造 Issue、验证结果、发布状态；不写入凭据、授权记录、私有采集数据或其他敏感内容。

推荐范围包括 `prototype`（通用流水线）、`figma`（桥接与原生操作）、`business`（离线业务套件）、`react`、`capture`、`html`、`documents`、`repo`（仓库治理）、`deps`、`release` 和 `ci`。新范围须能对应清晰的长期模块，避免同义名称。

类型按实际改动选择：

- `feat`：新增功能或用户可感知的能力；新增能力不能因规模小而写成 `fix`。
- `fix`：修复已有缺陷或回归。
- `refactor`：改变内部结构，保持外部行为。
- `perf`：有明确性能目标，保持功能语义。
- `docs`：文档新增或修订。
- `test`：测试新增或修订；是否纳入某次提交仍服从用户明确范围。
- `style`：仅视觉样式或不影响逻辑的格式调整。
- `build`：构建系统、打包脚本或构建依赖调整。
- `ci`：持续集成、检查或部署流水线调整。
- `chore`：其他日常维护；普通依赖更新使用 `chore(deps)`，版本更新使用 `chore(release)`。
- `revert`：撤销已有提交。

合法标题示例：

```text
feat(figma): 支持可恢复的原生文字修订
fix(react): 正确解析字段必填布尔值
docs(repo): 统一仓库提交规范与开发入口
chore(deps): 将 zod 升级至 3.25.76
```

`更新代码`、`Fix(figma): 修复恢复状态`、`fix(figma):修复恢复状态`、`fix(figma_ui): 修复恢复状态`、`fix(figma): Fix recovery state` 均不合规。`fix(figma): 修改一下` 即使形式正确，也因目的不明确而不合规。

## 原子边界与文件归属

一个提交表达一个完整意图，具备清晰的依赖、验证和回滚边界。按交付行为拆分，不按目录、改动行数或压缩包拆分。

- 完成该意图所需的实现、类型、必要文档及生成结果应同批纳入；通常同时纳入相关测试。多个步骤只能整体运行或发布时，应合成一个完整提交。
- 可独立交付的功能、修复、公共重构、构建变更、依赖升级、环境切换和规范治理分别提交；版本号更新独立于业务改动。
- 新功能尚未提交时，开发期间发现的缺陷直接修正后随首次 `feat` 交付，不刻意先提交有缺陷版本再补 `fix`。
- 共用文件可以按修改块归属不同提交，但每批必须在基线与前序提交上独立成立。不能依赖后续或未提交文件，也不能用完整工作树通过替代候选内容验证。
- 用户明确排除测试时，保留并运行本地测试，将例外和证据局限记录在提交计划或评审中；不能通过移动、改名把测试夹具伪装成生产文件纳入提交。
- 生产入口不得依赖被排除的本地测试、报告或采集数据。文档中的命令和链接须与拟提交内容相符。

插件先修改源文件，再用本仓库命令生成产物：

```powershell
npm --prefix .research/local-figma-bridge-poc run build:plugin
npm run check:bundle
```

`plugin/code.js` 同时含手写入口和生成区，禁止手工编辑生成区。多个提交共用运行时源文件时，应为每批准确源码分别生成相应产物，不能在第一批提前纳入所有后续功能。许可证只随真实依赖或生成内容变化纳入，不夹带无关行尾差异。

持久契约和操作说明随能力更新；临时计划、历史验收快照及本地证据按任务范围保留在忽略的 `.local/`。不得提交 `prototype-output/`、`test-results/`、凭据或私有采集数据。已有历史文档保留，不为统一规范改写历史。

## 分支、授权与暂存

日常开发使用 `dev`，不因本规范新建功能分支。同步远端、变基、推送及发布须遵守各自授权边界；不要为了整理提交而自动处理脏工作区。版本发布另按项目发布规范执行，版本号仅在线上分支准备发布时独立修改。

提供提交计划、标题或规范文档不等于获得执行授权。没有明确请求，不执行暂存、提交、分支操作、推送、PR、合并或发布。不得为统一格式而重写已经共享或发布的历史。

获准提交后依次执行：

1. 核对分支、HEAD、已有暂存内容、全部未提交文件及适用指令，冻结精确路径和修改块清单。
2. 在隔离候选目录核对本批与前序提交的依赖闭包；不覆盖主工作树已有生成物，不将本地测试叠加结果混称为干净候选验证。
3. 执行适用检查，审查新文件、删除、生成源和产物，确认没有敏感数据、临时文件或无关格式化。
4. 使用精确路径或修改块暂存，保留用户已有暂存内容。避免 `git add .`、`git add -A` 等全量暂存。
5. 检查暂存区实际内容，并复核最终提交信息；任何信息或暂存内容变化都应重新核对。
6. 提交后检查实际文件列表、HEAD 和剩余状态，确认测试排除及其他用户修改均保留。

每次提交前至少检查：

```powershell
git status --short
git diff
git diff --cached
```

## 验证与自动校验边界

按实际影响选择检查，命令以 [package.json](../package.json)、[桥接包](../.research/local-figma-bridge-poc/package.json) 和 [CI](../.github/workflows/prototype.yml) 为准：

- 文档：核对格式、链接、示例、命令和实际实现。
- 代码：先执行受影响测试，再执行适用的 `npm test`、`npm run acceptance`。
- 插件：重新生成，并运行 `npm run check:bundle`；生成结果应与相应提交的源文件一致。
- 浏览器行为：运行 `npm run test:browser`，保持串行；准备 Chromium 的安装步骤见仓库指南。
- 依赖或配置：检查清单与锁文件一致，并执行适用构建、审计和 CI 检查。

验证记录明确使用 `PASS`、`FAIL`、`NOT RUN`，记录对应源码或候选摘要。跳过、超时、取消和未运行均不是通过。完整工作树、本批候选、本地追加测试、浏览器、真实 Figma、后端及部署结果分别记录；构建或 mock 通过不能证明真实集成成功。

截至 2026-10-20，本仓库未配置 commitlint、Husky `commit-msg` 或 CI 提交信息检查；当前落地的是文档约束，提交前须人工逐项复核。ArchiveLens 的 pnpm、hook 初始化和 CI 配置不能直接当成本仓库已生效的能力。本次文档落地不安装依赖、不修改 Git hook 配置。

如后续引入自动校验，配置须与本文一致，先核对有效 `core.hooksPath` 并保护已有配置；只检查新增提交，不追溯整改共享历史。Agent 不得通过 `--no-verify`、提交时设置 `HUSKY=0`、修改或移除 hook、改变 `core.hooksPath`、弱化规则等方式绕过已配置检查。失败须修正重验，无法完成适用检查时报告阻塞，不能宣称可提交。CI 检查和远端必需检查需分别配置、核实，不因添加本地文件而视为启用。

## 破坏性变更与撤销

不兼容改动在冒号前加 `!`，并在正文或 `BREAKING CHANGE:` footer 说明影响、迁移和恢复方式。不能只加标记而省略说明。

```text
feat(prototype)!: 调整交付清单结构

说明旧调用方受到的影响、必须执行的迁移及恢复方式。

BREAKING CHANGE: 明确旧格式不再支持的字段及替代方式。
```

撤销优先使用 Git 自动生成的 `Revert "原提交标题"` 与 `This reverts commit <完整 SHA>.`，保留 SHA，并补充原因、影响和恢复条件。这是普通标题格式的例外；手写撤销消息仍使用 `revert(<scope>): 中文说明`。不得通过手写反向修改隐藏撤销关系，不自动豁免合并或版本提交。

## Pull Request

PR 标题使用 `<type>: 中文说明`，与普通提交的带作用域格式分别遵守对应要求。描述使用中文，包含 `改动说明`、`主要改动`、`验证结果`、`风险与影响`、`关联信息`；没有关联内容填写 `无`。涉及可见界面变化时附截图，未执行验证须明确标记，不把离线演示或本地通过写成生产集成完成。

准备压缩合并时，最终消息遵守项目 PR 约定 `<type>: 中文说明`；这是该合并方式的特定格式，不授权绕过已有校验。若未来提交校验要求 scope，须先协调配置与合并策略，不能擅自禁用检查。
